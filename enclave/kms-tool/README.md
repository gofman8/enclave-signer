# RGB-swap KMS helper

`swap-kms-tool` links the official [AWS Nitro Enclaves SDK for C](https://github.com/aws/aws-nitro-enclaves-sdk-c/tree/cd61b6187c8b20867ba4368d1ae62c5790c0269a) used by `kmstool_enclave_cli`. The stock CLI generates only 16- or 32-byte keys and does not expose our encryption context. This adapter preserves the swap signer's 64-byte seed and constructs the four context entries: `application=utexo-enclave-signer`, `flow=rgb-swap`, `seed_id`, and `bitcoin_network`.

AWS implements TLS, SigV4, NSM attestation, RSA and CMS recipient decryption. The helper checks the actual KMS response key ARN, rejects plaintext responses, and requires a 64-byte recipient seed. Generation returns ciphertext only; recovery returns the seed. It connects over vsock to parent CID 3, port 8003; the configured region selects the authenticated KMS hostname and signing scope.

Rust invokes the helper with private stdin/stdout JSON pipes. Credentials are never passed in arguments or environment variables. Messages are bounded, owned credential/seed buffers are erased, core dumps are disabled, and each invocation has a 12-second limit. Failures use fixed exit codes consumed by Rust; raw service diagnostics are discarded. Signing and S3 persistence remain in their existing Rust components. Mint/burn images do not include this helper.

Build on Linux with `build/build-swap-kms-tool.sh`, or through the existing swap Dockerfiles. `build/swap-kms-dependencies.tsv` pins the official sources and `build/swap-kms-nsm.Cargo.lock` pins NSM's Rust dependencies. Security-fixed dependency versions are used instead of upstream's older sample Dockerfile pins. The installed prefix contains dependency revisions, licenses and the SDK patch identity. Native regression tests and local E2E tooling live on `kms-testing`.

The only SDK source change is [nitro-sdk-cleanup.patch](../../build/patches/nitro-sdk-cleanup.patch), applied to `source/rest.c`. With this helper's static credentials, signing calls back synchronously. A closed connection can report failure before the SDK starts its unconditional wait, leaving it blocked until the helper's deadline. The patch records completion under the request mutex and waits in a loop. It also initializes the two cleanup pointers before early failure paths, preserving the SDK's strict GCC build without suppressing uninitialized-variable diagnostics. High-level KMS methods use this same REST path; replace the patch when an official SDK revision fixes it.

The patch is limited to this helper's one-request process. The pinned AWS allocator aborts on out-of-memory, so the patch does not add handling for artificial allocation-`NULL` returns or general SDK resource cleanup. TLS, SigV4, attestation and CMS remain upstream implementations. Builds reject SDK changes beyond this exact patch.

The helper also retains the SDK's bootstrap reference until client cleanup to prevent premature event-loop destruction. Its CMS header is an upstream internal API installed verbatim, so both integrations need review when upgrading the SDK. The `kms-testing` branch retains their fault-path and recipient-response regression coverage.
