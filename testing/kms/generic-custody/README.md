# Generic KMS custody validation

Production commit `e0f4dfa9ce62865c8f172c1980bbb894cf6e4e6f` keeps KMS custody enabled only for RGB swaps while separating custody names and interfaces from signing-flow selection. Current mint/burn behavior and existing swap encryption context remain unchanged.

The local E2E run passed all 44 scenarios on clean source commit `d76ddd998fa1d079ba0f5c5b1e27268b010242f4`. It used freshly rebuilt enclave and parent binaries, the official unmodified SDK helper, and open-source KMS/IAM/STS/S3 emulation. It includes recovery of ciphertext generated by the pinned earlier client, with identical identity and signatures, 20 malformed helper-input checks and two foreign-flow policy denials.

`e2e-report.json` records the clean source, binary hashes, dependency provenance and individual scenarios. `verification.json` records the Rust profiles, parent and native checks, build wiring, and rejection of unsupported custody feature combinations. Default/swap/mint-burn suites passed 565/608/606 tests respectively, with nine existing ignored tests per profile; 51 parent tests and all Clippy profiles passed. Native tests verified required flow parsing and the unchanged four-entry swap encryption context. Dependency revisions, SDK source and linked SDK/NSM libraries were unchanged.

The current upstream base changes, including parent health endpoints and BFA validation, were synchronized into this test source before building. Apart from the test harness, it differs from production only in the existing local test feature/hooks and artifact exclusions.

No new EIF or real Nitro/AWS recipient-attestation validation was performed for this refactor. Mock NSM and local TLS/authorization fixtures do not prove real AWS service boundaries. Existing documented upstream SDK limitations remain.
